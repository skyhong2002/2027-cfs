# 回訪合作夥伴模擬操作：v1

測試日期：2026-09-20。角色：過去贊助過 SITCON 的企業品牌窗口，希望快速掌握 2027 合作重點、整理曝光需求，再交由內部確認或與主辦方洽談。

這是 agent 模擬檢視，不是真實企業訪談。使用 Playwright 與 headless Chromium 實際操作 `http://127.0.0.1:4321/2027-cfs/`，桌面 1440 × 1000、手機 390 × 844 各完整走過一次。測試於 title 修正後重新載入。未寄送任何 email，也未點擊開啟郵件程式。

## 操作結果

兩種尺寸均完成：首頁 →「已經認識我們？看今年重點」→ 比較方案 → 試選方案 C → 候選品項搜尋 → Badge 繩詳情 → 加入清單 → 加入開源築夢洽談需求 → 帶著清單聊聊 → 填表 → 產生合作信件草稿。

- 兩種尺寸都能產生含聯絡資料、自由文字、方案 C、Badge 繩與開源築夢需求的草稿。
- 草稿明確表示尚未寄出，提供複製內容備援；此次未實際寄送。
- 小計維持待確認，沒有把未知金額顯示成免費；開源築夢清楚標示未計入小計。
- 桌面 document width 1440 / viewport 1440；手機 390 / 390，未發現全頁水平溢出。
- 此路徑兩種尺寸都沒有 JavaScript pageerror。
- 手機選單能打開並導向方案區；等候平滑捲動結束後，highlights 與 plans 標題在固定導覽列下方約 88 px，未被遮住。
- 手機品項 dialog 能閱讀、加入、關閉；表單和草稿可閱讀。
- 2027 價格／權益尚未公布是正確限制。本次不把「沒有正式價目」當程式缺陷；以下問題集中於沒有价目時，選擇是否仍能保留有用需求。

## RP-01｜品牌曝光分類找不到網頁 Logo

優先度：P1。追蹤：[Issue #10](https://github.com/skyhong2002/2027-cfs/issues/10)。狀態：已修正，本機桌面與手機復測通過。

重現：在品項區選「品牌曝光」，搜尋「網頁」。顯示 0 項；保持「網頁」文字，改選「全部」，即出現「網頁 Logo 曝光」。

影響：回訪品牌窗口可能誤以為今年取消網站品牌露出，必須猜出它被放進另一個分類才能找到。

建議：將合作目標視為可重疊標籤，讓網頁／背板／錄影模板等曝光候選同時出現在品牌曝光。若資料尚無目標標籤，搜尋無結果時提供「在全部品項搜尋『網頁』」的直接操作與結果數。

驗收：選品牌曝光搜尋網頁能找到網頁 Logo，或一個清楚操作即可展開其他類別符合結果。

## RP-02｜「方案內含」讓待確認權益看起來已包含

優先度：P1。追蹤：[Issue #10](https://github.com/skyhong2002/2027-cfs/issues/10)。狀態：已修正，本機桌面與手機復測通過。

重現：試選方案 C，點品項區「方案內含」。出現 13 個候選品項，包含接駁車廣播、會場攤位、R0 影片等，但每張卡又寫「適用方案待確認」。

影響：篩選名稱像是在顯示所選 C 已有的東西；提醒文字與名稱相互衝突。價格未定仍可討論，但權益是否包含不能讓讀者自行猜。

建議：在正式權益未取得前改為「方案權益候選」，搭配「尚未確認任何方案包含內容」；避免使用「已含」「方案內含」及「避免重複計價」的完成式承諾。

驗收：使用者不會把目前 13 項讀成所選方案承諾交付的權益。

## RP-03｜方案 C 的合作方向在信件裡遺失

優先度：P1。追蹤：[Issue #14](https://github.com/skyhong2002/2027-cfs/issues/14)。狀態：待修；本輪桌面與手機復測仍可重現。

重現：選卡片上寫「想整合現場與數位曝光」的方案 C，不填自由敘述也能產生信件。草稿僅附 `方案 C — 待確認 (2027 價格與適用權益待確認)`，沒有保留原本合作方向。

影響：對窗口和收到信件的行銷組，C 只是 placeholder 代號；主管拿到清單看不懂選擇理由。現階段唯一有意義的差異恰好沒有傳遞到下一步。

建議：清單、複製、列印與草稿附上「合作方向：現場交流＋數位曝光」等當時所選描述；可將 A–D 表達為需求方向而非成熟方案級別。不要填入推定價格／權益。

驗收：只選方案 C、留空自由敘述產生信件，收件者仍能讀出使用者想整合現場與數位曝光。

## RP-04｜「今年重點」與「一次看懂差異」承諾超過現有資料

優先度：P2。追蹤：[Issue #1](https://github.com/skyhong2002/2027-cfs/issues/1)。狀態：核心承諾與矩陣呈現已修正，本機復測通過；本屆正式合作內容仍依 [Issue #13](https://github.com/skyhong2002/2027-cfs/issues/13) 待補。

重現：從首頁回訪入口進入「今年，從這裡開始」。三項分別為開源築夢、方案比較、合作清單；後兩項是網站操作方式。再進方案比較，17 列 × 4 欄全部待確認。

影響：我本來要確認本屆活動對品牌有哪些新機會，卻得到兩項介面功能。比較表很大，但不能幫助排序；「一次看懂方案差異」會增加失落。

建議：改成「2027 合作進度／目前可以先談的事」，直接列「日期與場地已確認」「開源築夢規劃中」「正式方案與權益待公布」。在資料待定時，完整矩陣預設收合為「待確認的權益項目」，主要引導選需求方向與提出問題。保留矩陣以測試未来有正式資料時的資訊流。

驗收：回訪者在第一個入口就知道哪些本屆資訊已確認、哪些還不能比較，以及現在能提交什麼需求。

## RP-05｜多張候選卡只有同一句待確認，選配價值有限

優先度：P2。追蹤：[Issue #5](https://github.com/skyhong2002/2027-cfs/issues/5)。狀態：候選用途已補，本機首屏與搜尋品項復測通過。

重現：依序查看 Badge 繩、T-shirt、帆布袋、導遊團等候選卡；內文是相同的「2027 合作候選品項：名稱。呈現方式、執行規格、提供數量及適用方案待確認」。打開 Badge 詳情後，仍主要重複這段。

影響：我能辨認名稱，但無法比較品項適合現場互動、長時間攜帶曝光，或導流到產品。資訊流已可走通，決策資料還不足。

建議：在不承諾未知規格／數量的前提下，補充「可洽談的需求」：例如 Badge 繩可洽談活動識別配件品牌露出；官網 Logo 可洽談品牌介紹與外部連結；攤位可洽談現場作品／產品交流。每個候選一至兩句，使用「希望／可洽談」，避免假定已確認提供。詳情則列需要確認的問題，讓加入清單有用途。

驗收：至少首屏候選卡能讓回訪者選出符合目標的方式，並將不確定問題帶進洽談；不增加無來源的價格、名額或曝光成果。
